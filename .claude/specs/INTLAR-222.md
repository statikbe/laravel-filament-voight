## Problem statement

The package's five Filament resources have grown organically and the record pages stack an infolist above a variable number of relation managers, so a Project page is a long scroll of four sections plus three tables. Filtering is inconsistent to the point of being unusable for the tool's actual job: `severity` — the primary column on every findings table — cannot be filtered **anywhere**, because `Vulnerability::severity` is an appended accessor derived from `vulnerability_score` (`src/Models/Vulnerability.php:37,56-59`) and every filter must therefore route through `Severity::scoreRange()`. Three tables carry byte-identical copies of the `package_type` filter closure and two carry copies of `latest_only` + `observed_at`. Several enums (`DependencySyncStatus`, `VulnerabilitySource`, `AlertChannel`, `AlertFrequency`, `AuditRunStatus`) are dead or near-dead in the UI.

Alongside that, mapping the flows turned up a set of genuine defects (empty modals, a conditional field that never reacts, a bulk-delete path that bypasses an integrity guard, an `UnhandledMatchError` waiting to happen, an N+1) and a **red baseline**: the documented `composer test` command exits 1 with no output at all, one test fails, and phpstan reports one error.

25. **(mechanism corrected — CL-17)** `SelectConstraint::options()` is **not** an authorization boundary, and any scoping belongs in `modifyQueryUsing` or the table's own relationship scope. **The stated mechanism was wrong:** the spec claimed a forged value "reaches `whereIn` without being validated against the options list". It does not. `Select::getInValidationRuleValues()` (`vendor/filament/forms/src/Components/Select.php:1733`) derives an `in` rule from `options()`, and `QueryBuilder::tapOperatorFromRule()` catches the resulting `ValidationException` and returns (`vendor/filament/tables/src/Filters/QueryBuilder.php:352-356`), so the rule is **dropped in silence**. Verified in source by the orchestrator. The real failure mode is therefore **fail-open on the rule** — the constraint meant to narrow the query simply disappears, returning *more* rows — not value smuggling. The conclusion is unchanged and firmer: `options()` **hides, it does not deny**. Pinned by `tests/Feature/Resources/QueryBuilderOptionForgeryTest.php`, and the corrected explanation ships as a comment in `FilamentVoightServiceProvider`.

## Technical approach

**Tabs (AC 5–9) — hybrid, because the framework only offers one content tab.** `ViewRecord::content()` delegates to `getRelationManagersContentComponent()` (`vendor/filament/filament/src/Resources/Pages/ViewRecord.php:203-217`), which builds `Tabs::make()->key('relationManagerTabs')->livewireProperty('activeRelationManager')->contained(false)` and — when `hasCombinedRelationManagerTabsWithContent()` is true — prepends exactly **one** synthetic tab via `array_replace(['' => null], $tabs)` (`Concerns/HasRelationManagers.php:134-145`). So:

- **Customer, Team, Package (AC 7)** need only `hasCombinedRelationManagerTabsWithContent(): bool` + `getContentTabLabel()`. Note the `||` at `HasRelationManagers.php:134` means this works with a *single* relation manager too, which is why Customer and Team benefit.
- **Project (AC 5–6)** needs 7 sibling tabs, which that path cannot express. Override `content(Schema $schema)` on `ViewProject` and build one `Tabs` containing 4 content tabs (the existing sections, extracted into reusable builders) plus 3 tabs each embedding its relation manager through `Filament\Schemas\Components\Livewire::make($rmClass, ['ownerRecord' => …, 'pageClass' => static::class])->lazy()` — the same mechanism Filament itself uses at `HasRelationManagers.php:165-173`. Use `Tabs::persistTabInQueryString()` for URLs, which supersedes and improves on the `activeRelationManager` string keys added in `fefc205`. Relation-manager badges do not come along automatically on this path, so set them explicitly on the `Tab` where wanted.
- **Vulnerability (AC 9)** has no relation managers at all, so it is a plain schema-level `Tabs` inside `VulnerabilityInfolistSchema`.

**Reuse.** `Severity::scoreRange()` is the existing, tested (`tests/Enums/SeverityTest.php`, 10 tests) bridge between the accessor and queryable scores — every severity filter routes through it, following the pattern already in `KnownVulnerabilitiesRelationManager.php:78`. All 7 enums expose `options()` via `src/Enums/Concerns/HasOptions.php:10`, drop-in for `SelectFilter::options()` / `SelectConstraint::options()`. `AuditRun::latestIdsPerEnvironment()` (`:67`) / `latestIdsPerProject()` (`:82`) are the existing "current state only" subqueries. `Package::projects()` and `Project::findings()` are existing `HasManyDeep` relations that no filter currently uses.

**Conventions to hold.** `voightTrans()` only (never `__()`/`trans()`); one lang file with the established block order; new tab keys under `models.<model>.tabs.<slug>`; schema logic in static `configure()` methods under `<Resource>/Schemas/`; read-only resources define their infolist on the **page**, not the resource. Tests use `Livewire::test()` (the imported class, not the pest `livewire()` helper — the plugin is installed but unused), relation managers get `['ownerRecord' => $m, 'pageClass' => SomePage::class]`, pages get `['record' => $m->getRouteKey()]`, auth is `$this->actingAs(new User)` with `Illuminate\Foundation\Auth\User` (there is no users table or user factory).
